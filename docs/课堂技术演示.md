# 课堂技术演示：抢票、候补与库存一致性

计划让约 70 人抢 10 张票时，按已彩排的 [课堂演示手动 Runbook](课堂演示手动Runbook.md) 操作。下文的“留 3 张”是人数较少时的短演示方案。

## 演示目标

让全班对**同一车次、同一席别、同一起讫站**抢少量余票；售罄后提交候补；再退掉一张模拟乘客的票，观察候补自动兑现。订票、支付和候补预付均为课程模拟交易，不涉及真实资金。

## 课前预置（建议留 3 张）

1. 双击项目根目录 `start.cmd`，等启动窗口显示 `CR12306 is ready`。打开用户端和 `admin-login.html`，确认 `/api/health` 返回 `ok: true`。
2. 进入管理端 **AI 订票员 → 定向压测**。选一趟仍有余票的车次和席别。商务座总量通常只有 10 席，适合短演示。
3. 在 **指定乘车区间** 中选同学稍后要搜的**准确起讫站**。记下车次、席别、出发站、到达站；不能只记城市。
4. 将 **课堂演示预留张数** 设为 `3`，点击 **按实时余票计算订票人数**。页面会把模拟人数设为“该区间当前余票 − 3”，并自动设置 100% 模拟支付、2 个并发线程、关闭模拟乘客候补。
5. 点击 **启动 AI 订票任务**，等待进度达到 100%。检查“完成支付”数量；重新选择该席别与区间读取实时余票。若有个别任务失败，可再计算一次人数并补跑。以**区间余票**为准，不以“全程空闲席位”或车次总占用率为准。
6. 在用户端用另一浏览器或手机，按**指定车站**而非“城市全部车站”搜索，确认这趟车该席别显示约 3 张。课前不要让同学先提交订单。
7. 如需全班手机访问，运行 `start-tunnel.cmd`，用手机流量验证临时 URL。只分享用户端地址；管理端留在自己的投屏设备上。

## 台上操作顺序（约 5 分钟）

1. **亮出余票**：管理端展示指定车次和区间还剩 3 张；告诉同学搜索同一起讫站和席别。
2. **同时抢票**：发用户端地址，让同学同时提交。几人成功，其余人在余票刷新后看到“候补”。在管理端依次看 **流量缓冲 → 订单与乘客 → 候补队列**。
3. **提交候补**：请至少一位未抢到的同学点击“支付并候补”，在“我的订单”确认状态为“候补中”。这是模拟预付，会记录到 `wait_payment`。
4. **释放一张票**：在管理端 **AI 订票员 → AI 用户订单与退票**，筛选该车次，找到**刚才预置且起讫站相同**的一笔已支付 AI 订单，点击该行“退票”。优先逐笔退票，便于看到“一张释放 → 一个候补兑现”；不要用按车次随机批量退票来证明指定区间的兑现。
5. **观察结果**：候补队列应从“排队中”转为“已兑现”；同学的“我的订单”出现已支付车票。管理端再看订单和实时余票。释放的座位可能立即被候补占用，因此余票不一定短暂增加。

## 讲解时对应的数据库机制

- **区间位图**：每个物理座位的一行 `occupied_mask` 记录相邻站区段。例如 A→C 占前两位，C→D 仍可复用；A→C 与 B→D 因重叠不能共用该座位。
- **并发防超卖**：前端余票只是快照。同学从用户端提交的订票先进入 MySQL 的 `booking_request_buffer`；工作线程领取请求，最终在 `sp_create_order_hold` 的事务和行锁内重新判断位图。用于预置库存的 AI 任务直接调用同一个锁座过程。Redis 只唤醒用户端订票线程，MySQL 是可靠队列和权威库存。
- **候补自动兑现**：`wait_request` 保存候补顺序与状态。退票释放位图后触发定向匹配；后台线程还会周期补偿。匹配复用普通锁座流程，再将模拟预付款应用到订单。
- **可验证不变量**：订单、座位分配和位图应一致。课堂上如需数据库证据，可执行：

  ```powershell
  docker exec mysql84 mysql -uroot -p123456 CR12306 -N -e "SELECT COUNT(*) FROM v_inventory_reconciliation WHERE is_consistent=0;"
  ```

  预期输出 `0`。这是位图与有效分配的对账结果，比只展示“成功订单数”更能说明没有库存漂移。

## 可直接照着讲的串词

> “现在这趟车的这个区间和席别只剩 3 张。请大家同时提交，页面上的余票会刷新，但它只是某一刻的快照。真正决定谁买到票的是 MySQL 事务里的座位位图和行锁。”

> “没有买到的同学可以进入候补。我们现在从管理端退掉一张同一区间的模拟车票，系统会释放它占用的区段，然后自动按候补队列尝试分配。大家注意候补状态和我的订单会变化。”

> “最后看库存对账：有效订单的座位分配与实际位图一致，异常记录为 0。这样展示的不只是页面数字，而是并发购票、退票和候补之后数据库仍保持一致。”

## 现场提醒

- 当前项目固定售票演示日期为 **2026-10-07**，这是模拟运行日，不能讲成真实当天车票。
- 学生必须搜与预置一致的**具体车站和席别**；按城市搜索可能选到同车次的其他站对。
- 候补只能在该区间确实无票时提交。若仍有余票，先让同学完成抢票，或再用同一区间补充预置。
- 若候补先于退票被其他人的退票兑现，直接解释自动匹配已经生效，再用新的候补者复现即可。
- 演示结束后关闭 tunnel；数据库演示数据会保留，下一次应重新读取余票后计算预置人数。
