# 售票域逻辑模型与 DDL 评审说明

> 状态：v0.1，已于 2026-09-07 执行  
> 对应迁移：`database/migrations/V002__ticketing_domain_schema.sql`

## 1. 本阶段结论

本阶段只冻结数据结构，不设置列车运载量。编组、车厢和席位表已经定义，但保持空表；`train_run.formation_id` 允许为空。后续确定容量时，通过独立迁移插入编组数据并生成 `train_run_seat`。

现有 `station`、`train`、`train_station`、`train_segment` 均保留，不进行破坏性重建。

## 3. 标识符选择

- 静态车次继续以 `train_no` 为主键，避免无意义地重写现有外键。
- 动态业务统一使用无符号 `BIGINT` 代理主键。
- `train_run` 用 `(train_no, service_date)` 保证一个模拟日只有一个同名运行实例。
- 对外订单号、候补号和支付请求号与数据库代理主键分离。
- 所有客户端重试使用业务幂等键，不依赖前端“只点击一次”。

## 4. 时间类型选择

- 静态时刻模板：`TIME + day_offset`；
- 具体销售窗口、订单过期和支付时间：`DATETIME(6)`；
- 纯审计创建时间：`TIMESTAMP(6)`；
- `service_date` 指裁剪后长三角区域运行片段起点的服务日，不是区域外原始始发站日期，也不是每个经停站的自然日期。

V002 只增加允许为空的 day offset。V003 完成清洗后，才能将适用字段收紧为非空。

## 5. 金额选择

金额使用 `DECIMAL`，禁止使用 `FLOAT/DOUBLE`。订单项保存价格快照，订单总额必须等于订单项快照之和。该跨行不变量由受控事务和对账查询保证。

## 6. 状态字段选择

状态字段使用 `VARCHAR + CHECK`，而不是 MySQL `ENUM`：

- 数据库仍能拒绝非法状态；
- 后续增加状态时可以显式修改约束；
- 状态集合在 DDL 中清晰可见；
- 避免业务代码过度依赖 MySQL 专有枚举行为。

## 7. 库存字段选择

`train_run_seat.occupied_mask` 使用 `BIGINT UNSIGNED`。现有数据最大 11 个相邻区间，V002 将运行实例限制在最多 63 个区间，避免有符号移位和最高位边界造成歧义。

没有为 `occupied_mask` 单独建立 B-Tree 索引，因为以下条件通常不可 sargable：

```sql
(occupied_mask & :request_mask) = 0
```

查询会先通过 `run_id` 将扫描范围限制到一趟列车的席位，再进行位运算。将不可用的索引加入设计只会增加每次库存更新的维护成本。

## 8. 数据库能够直接保证的约束

- 主键与外键完整性；
- 站码、订单号、幂等键、支付请求号唯一；
- 相邻区间站序连续；
- 票价和订单金额非负；
- 起点序号小于终点序号；
- 席位分配掩码非零；
- HOLD 必须有过期时间；
- RELEASED 必须有释放时间；
- 状态值来自有限集合；
- 一个订单项最多对应一条席位分配历史；
- 候补最多转换为一笔订单。

## 9. 需要由受控事务保证的跨表约束

普通 `CHECK` 和外键无法表达以下规则。V004 已实现第一批库存事务，剩余规则将在后续迁移继续补充：

- 订单项的起止序号不超过该运行实例的停站数；
- `seat_allocation.segment_mask` 与起止序号完全一致；
- 分配的席位属于该运行实例所使用的编组；
- 分配席别与订单项请求席别一致；
- 同一席位的有效区间不能重叠；
- 当前位图等于全部有效分配掩码的按位或；
- 多人订单必须整单成功或整单回滚；
- 支付、取消和超时不能重复释放同一分配；
- 同一乘车人不能持有时间重叠的有效行程；
- 订单总额等于订单项价格快照之和。

应用账户最终只获得查询权和受控过程执行权，不直接获得库存核心表的任意更新权。

## 10. 审计设计

`order_event` 与 `inventory_event` 是只追加事件表：

- 当前状态读取订单和库存当前表；
- 历史解释读取事件表；
- 每次库存变化保存变更前、变更后位图；
- `trace_id` 将一次业务事务内的订单和库存事件关联起来；
- 事件表不负责异步消息投递，因此当前不需要消息队列或 Outbox 基础设施。
