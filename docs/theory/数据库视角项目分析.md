# CR12306 项目分析——数据库视角

> 本文依据当前项目的 MySQL V002—V014 迁移、Neo4j 查询投影和 Web 接口实现整理。重点说明数据库如何支持查询、库存、订单、退票和候补，而不是介绍页面样式。

## 一、数据整体架构

### 1. 总体结构

系统采用 **MySQL + Neo4j** 的组合架构：

```text
用户端 / 管理端
        ↓
Python API 层
   ├─ MySQL：车次、票价、库存、订单、支付、退款、候补的唯一事实源
   └─ Neo4j：负责换乘路径和车次组合的候选搜索
                    ↓
             候选结果返回 MySQL
             再检查时刻、票价和实时库存
```

核心原则是：**Neo4j 负责“找路”，MySQL 负责“能否出售”和“实际扣票”**。因此即使图数据库的数据同步稍有延迟，也不会造成超卖。

### 2. 数据表

当前数据库共形成约 25 张核心表，可按职责分为以下几组。

| 分类 | 主要表 | 负责的功能 |
|---|---|---|
| 静态铁路网络 | `station`、`train`、`train_station`、`train_segment` | 保存车站、车次模板、停站顺序和相邻运行区段，是时刻查询和图数据库投影的基础 |
| 编组与座位 | `seat_type`、`formation_template`、`carriage_template`、`seat` | 描述席别、列车编组、车厢和具体物理座位，使容量可配置而不是写死在程序中 |
| 当日运行与库存 | `train_run`、`train_run_seat` | `train_run` 表示某日的一次实际开行；`train_run_seat` 保存该次运行中每个座位的区间占用位图 |
| 距离、票价与销售 | `station_pair_distance`、`fare_rule`、`run_fare` | 保存相邻站距离、列车类型/席别计价规则，以及具体运行实例的 OD 票价产品 |
| 用户与乘车人 | `app_user`、`passenger` | 区分登录账户和实际乘车人，一个账户可管理多个乘车人 |
| 订单交易 | `ticket_order`、`order_item`、`seat_allocation` | 分别保存订单头、每位乘客的一张票，以及具体分配到的座位和占用区间 |
| 支付退款 | `payment`、`refund` | 保存支付和退款请求，使用唯一业务号实现幂等，防止重复支付或重复退款 |
| 候补 | `wait_request`、`wait_passenger` | 保存候补条件、座位偏好、截止时间和候补乘车人 |
| 审计事件 | `order_event`、`inventory_event`、`wait_request_event` | 以只追加方式记录订单、库存、候补状态变化，便于追踪、对账和故障分析 |

其中，`seat_allocation` 不删除已经释放的记录，而是将状态改为 `RELEASED`。这样既能保留完整历史，也能知道某一段库存为什么被占用或释放。

### 3. 视图

| 视图 | 作用 |
|---|---|
| `v_train_run_stop` | 将服务日期、到发时间和跨日偏移合成为完整 `DATETIME`，解决跨午夜列车的时间比较问题 |
| `v_inventory_reconciliation` | 对比座位当前位图与有效分配应占位图，发现库存不一致 |
| `v_order_amount_reconciliation` | 对比订单总金额和明细票价之和，发现订单金额异常 |
| `v_wait_queue` | 展示候补队列位置、跳过次数和公平保护状态 |
| `v_order_detail` | 聚合订单、乘客、车次、站点、席别、车厢和座位，供用户端与管理端直接读取 |

视图的作用是把复杂联表逻辑封装成稳定的“读取接口”，减少页面和应用层重复拼接 SQL。

### 4. 函数、存储过程与触发器

#### 函数

- `fn_segment_mask(from_order, to_order)`：把乘车区间转换为 64 位区间掩码，是位图库存模型的基础。

#### 主要存储过程

| 存储过程 | 作用 |
|---|---|
| `sp_query_availability` | 查询某车次、OD 区间和席别的精确余票 |
| `sp_query_position_availability` | 查询 A/B/C/D/F 等位置偏好的余票 |
| `sp_create_order_hold` | 在事务中创建订单、分配座位并预占库存，是最核心的订票过程 |
| `sp_confirm_order_payment` | 幂等确认支付，将预占座位转为正式确认 |
| `sp_cancel_unpaid_order` | 取消未支付订单并释放其区间位图 |
| `sp_expire_order_holds` | 批量关闭超时订单，通过 `SKIP LOCKED` 支持多个工作线程并行处理 |
| `sp_refund_paid_order` | 处理已支付订单退款并准确释放原占用区间 |
| `sp_create_wait_request` | 无票时创建候补请求，并验证当前是否确实不能直接购票 |
| `sp_cancel_wait_request` | 取消尚未兑现的候补请求 |
| `sp_match_wait_requests` | 按 FIFO 和公平保护规则兑现候补，并复用普通占座过程 |
| `sp_search_direct_trains` | 查询直达车次、票价、总余票、偏好位置余票和整单可满足状态 |
| `sp_validate_transfer_candidates` | 对 Neo4j 给出的换乘候选进行 MySQL 权威复核 |
| `sp_register_demo_account` | 为演示用户创建或读取账户与默认乘车人 |

#### 触发器

- `trg_order_item_passenger_itinerary_guard`：插入车票明细前锁定乘车人，检查时间区间是否与其已有有效行程重叠，防止同一乘客同时乘坐两趟时间冲突的列车。
- `trg_ticket_order_sync_wait_status`：候补生成的订单在支付、取消或超时后，自动同步对应候补请求的最终状态。

## 二、现实购票问题的数据库处理流程

### 1. 搜索 A 到 B 的车票

1. 用户可以选择具体车站，也可以只选择城市；城市会在应用层展开为该城市的所有车站组合。
2. MySQL 在 `v_train_run_stop` 中查找同时经过 A、B 且 A 的停站序号小于 B 的运行实例。
3. 连接 `run_fare` 获取该 OD 区间各席别票价。
4. 调用 `fn_segment_mask(A序号, B序号)` 生成请求区间位图。
5. 对该运行实例的每个座位判断：

```text
occupied_mask & request_mask = 0
```

结果为 0 表示该座位在 A→B 全程没有任何重叠占用，可以出售。

6. 按席别聚合可用座位数，返回出发时间、到达时间、票价、余票和位置偏好余票。

搜索结果只是瞬时快照，真正下单时仍会重新加锁检查，避免查询后库存被其他用户抢走。

### 2. 为什么使用“区间位图”管理余票

假设列车经过 A—B—C—D，共有三个相邻区段，每一位表示一个区段：

```text
A→B = 001
B→C = 010
C→D = 100
A→C = 011
B→D = 110
```

某座位已售 A→C，则其位图为 `011`。此时：

- B→D 的请求为 `110`，与 `011` 按位与不为 0，因此冲突；
- C→D 的请求为 `100`，与 `011` 按位与为 0，因此同一座位可以继续出售。

这解决了铁路库存最关键的问题：**同一座位可以在不重叠区间复用，但任何重叠区间都不能重复出售。**

### 3. 预订座位与防止超卖

`sp_create_order_hold` 的核心流程为：

1. 验证用户、乘车人、运行实例、起止站序、席别和开放票价；
2. 检查 `(user_id, idempotency_key)`，重复请求直接返回原订单；
3. 将乘车人 JSON 数组通过 `JSON_TABLE` 转为内存临时表；
4. 按固定顺序选择候选座位，并使用 `SELECT ... FOR UPDATE` 加行锁；
5. 获得锁后再次检查位图，防止其他事务已经占用；
6. 优先选择指定的 A/B/C/D/F 位置，偏好无票且允许兜底时选择其他空闲座位；
7. 写入 `ticket_order`、`order_item`、`seat_allocation`；
8. 使用按位或更新库存：`occupied_mask = occupied_mask | request_mask`；
9. 写入订单和库存事件后提交事务。

如果多人订单中有任何一人无法分配，整个事务回滚，不会出现“同行五人只买到三张”的部分成功。

### 4. 支付、取消和超时

- **支付成功**：订单从 `PENDING_PAYMENT` 变为 `PAID`，座位分配从 `HOLD` 变为 `CONFIRMED`。位图在预占时已经设置，因此支付时无需再次扣库存。
- **主动取消**：只允许取消未支付订单。数据库锁定订单、分配和座位后，清除相应区间位。
- **超时关闭**：`sp_expire_order_holds` 按批次领取到期订单，使用 `FOR UPDATE SKIP LOCKED`，多个清理线程不会重复处理同一订单。

释放库存使用：

```text
occupied_mask = occupied_mask & ~segment_mask
```

它只清除该订单占用的区段，不影响同一座位被其他订单占用的区段。

### 5. 退票后的余票处理

`sp_refund_paid_order` 的流程为：

1. 通过退款请求号检查幂等性；
2. 锁定订单，确认订单属于当前用户且状态为 `PAID`；
3. 按固定顺序锁定该订单的座位分配和 `train_run_seat`；
4. 检查位图仍包含该分配的完整区间，避免在不一致状态下继续退款；
5. 清除对应区间位，将分配改为 `RELEASED`，订单和明细改为 `REFUNDED`；
6. 写入退款、库存和订单事件；
7. 提交后，释放出的库存可供普通查询或候补匹配再次使用。

系统在退款或取消预占提交后立即按车次、席别定向调用候补匹配过程，并由每秒运行的后台线程补偿处理外部库存变化和到期请求。未来仍可引入事务 Outbox，将“库存释放”事件持久化后可靠唤醒独立候补消费者。

### 6. 候补队列

创建候补前，数据库会先检查当前库存。若能够直接满足整单，则拒绝创建候补，要求走普通购票流程。

候补兑现流程如下：

```text
WAITING → MATCHING → MATCHED_HOLD → FULFILLED
              └────→ WAITING / CANCELLED / EXPIRED
```

主要规则：

1. 基础顺序为 `created_at, wait_request_id`，即 FIFO。
2. 如果队首多人订单暂时无法整单满足，允许较小订单有限度越过，提高碎片库存利用率。
3. 每次被越过会增加 `skip_count`；达到 3 次后进入公平保护，后续请求不能继续无限绕过，避免大订单“饿死”。
4. 多个匹配线程使用 `FOR UPDATE SKIP LOCKED` 领取不同请求。
5. 实际兑现调用同一个 `sp_create_order_hold`，因此候补不会绕过普通购票的库存锁和防超卖规则。
6. 候补订单使用 `WAIT-{wait_request_id}` 作为幂等键。工作线程即使中断后重试，也不会重复创建订单。

### 7. 换乘查询

1. Neo4j 根据 `TrainRun—CALLS_AT—Station` 图关系枚举一次换乘候选。
2. 候选数量限制为最多 100 个，防止图遍历结果失控。
3. 候选以 JSON 传入 MySQL，并通过 `JSON_TABLE` 写入临时表。
4. MySQL 再检查两趟车是否在售、方向是否正确、换乘时间是否合理、两程票价和实时余票是否存在。
5. 最终下单仍分别进入 MySQL 库存事务。

## 三、还可以引入哪些数据库专业技术

引入更多数据库应以明确问题为前提，而不是为了增加技术数量。

| 技术或数据库 | 可解决的问题 | 在本项目中的合理用法 | 是否建议当前引入 |
|---|---|---|---|
| Redis | 热点读取、会话、限流 | 缓存车站、静态时刻表和热门查询；不能作为权威库存 | 可在压测证明 MySQL 查询压力较大后引入 |
| ClickHouse | 大规模统计分析 | 分析 AI 压测、订单趋势、热门 OD、候补等待时间，不影响交易库 | 适合后续管理端分析 |
| Elasticsearch / OpenSearch | 模糊搜索和日志检索 | 支持车站别名、拼音、错别字搜索，以及快速检索大量审计日志 | 数据量扩大后有价值 |
| TimescaleDB / InfluxDB | 时序指标 | 保存 TPS、P95 延迟、锁等待、死锁数、候补长度等监控数据 | 做性能实验时适合引入 |
| PostgreSQL + PostGIS | 空间数据分析 | 保存车站经纬度、计算路线距离、绘制铁路网络和区域查询 | 若要完善地图与真实距离可引入 |
| Kafka + Outbox/CDC | 可靠事件传递 | 退票后唤醒候补、发送通知、同步 Neo4j 和分析库，避免直接双写 | 系统服务化后再引入 |
| MySQL 只读副本 | 分离查询压力 | 管理报表、静态时刻和历史订单走副本；库存事务仍走主库 | 比立即更换交易数据库更实用 |
| 表分区与归档 | 控制大表规模 | 按服务日期分区 `train_run_seat`、订单和事件表，旧数据转入归档库 | 支持多日期和长期运行前引入 |

不建议把 Redis、Neo4j 或搜索引擎作为库存事实源。库存需要事务、行锁、唯一约束和可恢复性，仍应由 MySQL 统一决定。

## 四、当前提升效率与正确性的巧思

### 1. 一行位图代替多行区段库存

一个座位只用一条 `train_run_seat` 记录和一个 64 位整数表达最多 63 个运行区段。相比“每座位每区段一行”，显著减少行数、锁数量和更新次数。

### 2. 静态模板与当日实例分离

车次停站和物理座位属于模板数据，`train_run` 和 `train_run_seat` 才是每日实例。这样不必每天复制全部静态结构，同时又能让每天具有独立状态和库存。

### 3. 票价预生成与成交价快照

距离和票价提前生成到 `run_fare`，查询时无需实时重复计算。成交价写入 `order_item.price_snapshot`，历史订单不会受后续调价影响。

### 4. 确定性加锁顺序

座位通常按照车厢、座位或主键的固定顺序锁定。多个事务以相同顺序取锁，可以减少循环等待和死锁概率。

### 5. 查询快照与交易确认分离

搜索只负责快速返回当前余票；下单事务会在行锁内重新检查库存。用户看到的查询结果即使已经变化，也只会导致下单失败或选择其他座位，而不会造成超卖。

### 6. 幂等键代替“希望请求只发送一次”

订单、支付、退款和候补都设置唯一业务键。即使用户重复点击、网络超时重试或后台任务恢复，数据库唯一约束也能保证同一业务只执行一次。

### 7. `JSON_TABLE` 批量处理乘车人和候选

多人订单和换乘候选以 JSON 一次传入，再转换为内存临时表进行联接和校验，减少应用层多次往返数据库。

### 8. `SKIP LOCKED` 支持并行后台任务

超时订单清理和候补匹配使用 `FOR UPDATE SKIP LOCKED`。多个工作线程可以各自领取不同任务，不需要全局锁，也不会重复处理。

### 9. 视图与追加式事件兼顾读取和审计

视图为页面提供易读结果，事件表保留原始状态变化。前者减少重复联表，后者使问题可以回放和定位，而不必只依赖当前最终状态。

### 10. 图数据库只是可重建投影

Neo4j 不保存权威库存，MySQL 数据可以重新同步生成图。这样既使用了图数据库擅长的路径查询，又避免维护两份权威交易数据带来的分布式一致性问题。

## 总结

本项目的核心价值不是表的数量，而是围绕铁路售票的三个难点建立了完整数据库机制：

1. 使用区间位图解决座位在不同区间上的复用与冲突；
2. 使用事务、行锁、幂等键和状态机解决并发下单、支付、取消和退款；
3. 使用公平候补队列与 MySQL/Neo4j 两阶段查询解决无票兑现和复杂路径查询。

如果继续优化，优先顺序应是：先完成自动化并发测试和运行监控，再根据实际瓶颈引入缓存、分析数据库或消息系统，而不是直接增加更多数据库组件。
