# V013 优化说明

## 1. 售罄仍可点击预订

原数据库占座过程已经通过区间位图、`SELECT ... FOR UPDATE` 和带条件的 `UPDATE` 防止实际超卖，但客户端保留的是搜索时的余票快照。订单完成或其他用户抢票后，旧页面仍可能显示“预订”。

本轮采用三层保护：

1. 列表按钮按数据库返回的 `can_fulfill` 判断，不再只判断旧的余票数字；
2. 提交前调用 `/api/availability` 重新读取当前 OD 区间余票，售罄时立即切换为候补入口；
3. 最终消费请求时仍调用 `sp_create_order_hold`，在座位行锁内再次检查位图。即使多个用户同时看到最后一张票，也只有一个事务能成功。

## 2. 数据库流量缓冲

新增 `booking_request_buffer`，用户提交不再要求所有请求同时争抢库存锁，而是先持久化进入数据库队列。

- `(user_id, idempotency_key)` 唯一约束防止重复提交；
- `sp_claim_booking_requests` 使用 `FOR UPDATE SKIP LOCKED`，多个工作者可以领取不同请求；
- `lease_owner + lease_until` 形成消费租约，工作者崩溃后请求可自动重新入队；
- `sp_complete_booking_request` 只允许持有租约的工作者完成请求；
- 真正扣票仍复用原子占座和支付过程，不另写库存逻辑；
- `v_booking_buffer_monitor` 向管理端展示状态、尝试次数、耗时和错误。

这是一个适合课程规模的“数据库消息队列”。它展示削峰、幂等消费、竞争消费者和故障恢复，又不需要额外部署 Redis/Kafka。数据量和服务规模继续扩大后，可使用 Outbox + Kafka 替换调度部分，但 MySQL 仍应保留库存事实权威。

## 3. 候补监控

管理端候补页面现在能够：

- 查看等待、匹配、占座、兑现、取消和过期状态；
- 查看队列位置、跳过次数和公平保护状态；
- 每 2 秒自动刷新监控数据；
- 退款或取消预占后立即按车次和席别触发 `sp_match_wait_requests`；
- 后台线程每秒补偿扫描，处理外部库存变化和候补截止。

候补兑现仍调用 `sp_create_order_hold`，因此不会绕过库存锁，也不会发生普通购票与候补各自维护一套库存算法的问题。

## 4. 管理端隔离

新增 `admin_user` 与 `admin_session`：

- 管理员账户与 `app_user` 乘客账户完全分离；
- 密码使用 PBKDF2-SHA256、随机盐和 200000 次迭代保存；
- 登录失败 5 次后临时锁定；
- 浏览器只保存 HttpOnly、SameSite=Strict 会话 Cookie；
- 数据库只保存随机令牌的 SHA-256，不保存原始令牌；
- 所有 `/api/admin/*` 接口在服务端统一验证会话；
- 未登录访问 `/admin.html` 会跳转到 `/admin-login.html`；
- 普通用户页面没有管理端入口。

首次运行且管理员表为空时，服务根据 `CR12306_ADMIN_USER` 和 `CR12306_ADMIN_PASSWORD` 创建初始管理员。演示默认值为 `admin / RailFlow@123`，协作或展示前应通过环境变量修改。

## 5. 验收结果

### Redis 瞬时流量缓冲

在 MySQL 持久化请求队列之外，系统增加了可选 Redis 唤醒层。请求必须先写入 `booking_request`，之后才向 Redis 列表推送任务编号；工作线程使用阻塞读取感知新任务，再回到 MySQL 通过事务领取并执行。Redis 只表示“有新任务”，不保存订单事实，因此缓存宕机时可自动退化为 MySQL 轮询，既减少高峰期的频繁查询，又避免缓存数据丢失导致订单丢失。

根目录的 `start.cmd` 与 `start.ps1` 可自动启动 MySQL、Neo4j、Redis、数据库迁移和 Web 服务，具体操作见 [运行说明](../运行说明.md)。

- V013 已成功应用到本机 MySQL 8.4 容器；
- Python 服务端语法检查通过；
- 三份 JavaScript 文件通过 `node --check`；
- 未登录管理 API 返回 401；
- 未登录管理页面返回 302 并跳转到独立登录页；
- 管理员登录后总览与缓冲监控 API 返回 200；

- 候补监控接口必须登录，库存释放后可自动兑现候补。
