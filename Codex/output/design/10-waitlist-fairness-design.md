# V009 候补队列与公平兑现设计

## 1. 核心目标

候补不是简单的库存轮询。它需要同时保证库存不超卖、请求按合理顺序处理、多人订单整单兑现、匹配任务可恢复，以及大订单不会被后续小订单无限越过。

## 2. 候补请求

`sp_create_wait_request` 接收运行实例、OD、席别、A/B/C/D/F 位置偏好、是否允许兜底、1～5 名乘车人、幂等键和截止时间。数据库负责验证：

- 运行实例与票价处于可售状态；
- OD 能生成合法区间位图；
- 乘车人属于当前用户且有效；
- 幂等请求的业务参数与乘车人集合一致；
- 当前余票确实不足以直接满足整单，否则返回 `WAIT_DIRECT_INVENTORY_AVAILABLE`，提示走普通下单。

位置偏好会完整传递给实际占座过程。指定位置有余票时优先匹配；允许兜底时可按其他余票确定性分配；禁止兜底时只接受指定字母。

## 3. 公平策略

第一优先级是 FIFO，即 `created_at, wait_request_id`。如果队首多人订单暂时无法整单满足，允许后续较小订单越过，以提高碎片库存利用率；每次越过使 `skip_count + 1`。

采用阈值 3 的有界跳过：

- `skip_count < 3`：可以继续扫描后续请求；
- 第 3 次仍无法兑现：请求成为 `fairness_protected`，本轮匹配停止；
- 后续释放更多连续库存后，下轮仍首先尝试该请求。

这是一种公平性与利用率之间可解释的折中。严格队首阻塞最公平但容易浪费碎片；无限跳过利用率高但会让多人长区间订单饥饿。

## 4. 整单兑现和并发

匹配器不会预先减库存，而是调用已经通过并发验证的 `sp_create_order_hold`。该过程为整单事务：任何一个乘车人分配失败，所有位图置位、订单项和审计事件一起回滚。

多个匹配工作者通过 `FOR UPDATE SKIP LOCKED` 领取不同请求。请求先进入 `MATCHING`，并记录 `matching_started_at`：

- 成功后进入 `MATCHED_HOLD`，生成 10 分钟待支付订单；
- 库存不足时回到 `WAITING` 并增加跳过次数；
- 非库存类永久错误进入 `CANCELLED`；
- 工作进程崩溃留下的 `MATCHING` 请求，5 分钟后可以重新领取。

匹配订单使用 `WAIT-{wait_request_id}` 作为订单幂等键。即使工作者在创建订单后、回写候补状态前崩溃，重新执行也只会取回同一订单，不会重复占座。

## 5. 状态机

`WAITING → MATCHING → MATCHED_HOLD → FULFILLED`

辅助终态：

- 用户主动取消：`WAITING → CANCELLED`；
- 超过候补截止时间：`WAITING/MATCHING → EXPIRED`；
- 匹配订单取消或支付超时：`MATCHED_HOLD → EXPIRED`；
- 匹配遇到永久业务错误：`MATCHING → CANCELLED`。

订单支付后，通过数据库触发器把对应候补请求转为 `FULFILLED`。候补状态与订单事实通过 `matched_order_id` 一一关联。

## 6. 审计与观察

`wait_request_event` 只追加记录创建、领取、跳过、匹配、取消和失败事件。`v_wait_queue` 展示当前队列位置及 `fairness_protected`，便于课程演示 FIFO 与老化效果。

## 7. 为什么不使用 Redis/MQ

当前只有一天、1798 个运行实例，MySQL 的联合索引、行锁、`SKIP LOCKED`、事务与幂等键已经足够。引入 Redis 或消息队列会增加双写一致性，却不能提升本项目要展示的数据库知识。后台程序只需周期调用匹配存储过程；队列事实仍在 MySQL。

## 8. 验收标准

- 有直接余票时不能创建候补；
- 无票时可以创建且幂等重放返回同一请求；
- 多人请求不能部分兑现；
- A/B/C/D/F 严格偏好和允许兜底均符合普通购票规则；
- 多工作者不会领取同一请求；
- 匹配订单支付后候补状态为 `FULFILLED`；
- 匹配订单超时或取消后候补状态为 `EXPIRED`；
- 第三次跳过后停止继续越过；
- 库存对账始终一致。
